## 📖 项目简介

Canton 的隐私模型对机构是最大优势,对公共信任却是最难的问题:**不存在一个任何人
都能重算某个平台账目的公开账本。** Canton 上的交易所、托管方和资产平台,一直缺少
一种不泄露私有数据就能证明"托管资产 ≥ 用户负债"的标准方法。

本项目补上这块缺口:平台每日发布一份覆盖全部用户余额的密码学承诺;每位用户
**完全在自己的浏览器里**验证自己的余额被计入公开总额。原始数据永不离开平台的
participant 节点,公众看到的是承诺、证明与总额——与 Canton 本身相同的信任形态。

偿付能力证明只是建立在这套机制之上的**第一个披露 profile**,而不是它的全部。
同一套承诺、证明与验证内核,回答的是每一家进入 Canton 的机构都必须解决的更一般
的问题:*如何在不公开数据本身的前提下,向特定的对象证明一条关于私有账本数据的
特定陈述?* 储备覆盖、回购抵押充足性、基金 NAV 的资产支撑、原子结算保证、持有人
适格性——都是同一个形状,详见[披露 Profile](#-披露-profile)。

### 用大白话讲

**什么叫"用户负债"。** 你把钱存进交易所之后,那笔钱就不再是一堆贴着你名字的
硬币,而变成了**平台欠你的一笔债**。把平台欠每一位客户的钱加总起来,就是它的
**负债**。再拿它实际托管的资产来对照:如果资产 ≥ 负债,平台就是**有偿付能力
的**——所有人同时要求提现,也都能兑付。

**什么叫"重算"。** 任何平台都可以*声称*自己偿付充足,问题在于你是不是只能信
它一张嘴。在公链上你不必:任何人都能把账本拉下来,用原始数据把这笔账重新算
一遍,不需要谁批准就能得到同样的总数。这就是这里说的"重算"——自己把加法重做
一遍,而不是相信别人公布的那个数字。

Canton 有意不是这么设计的。余额是私有的——机构选择它恰恰是为了这一点——于是
外部没有任何人能把这笔账重算一遍。本项目要做的,是在不放弃隐私的前提下,把
"可核对"这件事还给你:

1. **平台做出承诺。** 每天把欠每一位客户的钱加总,并把这份完整名单——每一个
   客户、每一笔余额——压缩成一个 64 个字符的指纹,称为**树根**。名单里任何一笔
   余额改动一分钱,指纹都会面目全非;把它公布出来,平台就被钉死在某一个特定
   版本的账目上。
2. **平台公开发布。** 发布这个树根,以及它声称欠下的各项总额。
3. **你来核对。** 你下载一个很小的文件:你自己的余额,加上大约十七个中间
   指纹——一家有 10 万客户的平台,也就只需要这么多。你的浏览器把与你有关的
   那一小段加法重做一遍,确认它恰好落在公开的树根**以及**公开的总额上。

如果对得上,就说明你的钱确实被计入了平台向全世界公布的那个数字里,而且金额
正是给你看的那个。如果平台悄悄把你漏掉、把你的余额调小,或者少报了总额,
这一步就会失败——失败发生在你自己的电脑上,而不是它的服务器上。整个过程不
暴露任何人的身份:其他客户只以没有标签的指纹与小计的形式出现,而且盐值每次
快照都会更换,这些数字既对不上具体的人,也无法在不同报告之间被追踪。

**术语对照**

| 术语 | 大白话 |
|---|---|
| 用户负债 | 平台欠用户的钱 —— 所有客户余额之和 |
| 偿付能力 | 托管的资产 ≥ 欠下的负债 |
| 重算 | 自己用原始数据把账重新算一遍,而不是相信别人公布的数字 |
| 承诺(commitment) | 一大堆数据的短指纹,提前公开;之后再改数据,指纹一定对不上 |
| 叶子 / 树根 | 你个人的那一条记录 / 覆盖整份名单的那一个指纹 |
| 包含性证明 | 证明"你这条记录确实在名单里"所需的那几个额外指纹 |
| Merkle 求和树 | 让同一个树根既能证明"在名单里"、又能证明"总额没错"的结构 |
| 盐(salt) | 混进你那条记录里的随机值,别人无法靠穷举余额把它猜出来 |

## 🧭 为什么 Canton 上尤其需要它

在别的链上,偿付能力证明是公开数据之外的补充;在 Canton 上,它本身就是那份
公开数据——而且这个缺口是结构性的,不是平台"愿不愿意多披露"的问题。

### 对机构来说,"全部公开"是个错误的指令

不同对象有权知道的东西并不相同,而这中间的落差恰恰就是产品本身:

| 对象 | 必须能核对 | 不该看到 | 目前的替代品 |
|---|---|---|---|
| 终端投资者 / 客户 | 我的头寸被计入了;基金有资产支撑 | 其他客户的头寸 | 每月对账单 PDF |
| 交易对手方 | 我们未平仓交易背后的抵押品真实存在且覆盖敞口 | 平台的其他对手方及其规模 | 双边信任、追保 |
| 发行方 / 托管方 | 代币供应量与托管资产相符 | 客户层级的持仓分配 | 对账文件 |
| 审计师 | 整本账能对平、抽样是完整的 | (在 NDA 下有权看到全部) | 季度核验报告 |
| 监管机构 | 隔离、集中度与各项限额被遵守 | 超出监管范围的商业敏感细节 | 定期报送 |
| 公开市场 | 发行方有偿付能力、储备覆盖负债 | 任何可识别到客户的信息 | 新闻稿 |

每一行都是同一个密码学操作,只是对象不同、公开的子集不同。让每家机构各自定制
实现一遍,正是一个生态最终没有标准的原因。

### 再往下,原因是结构性的

- **没有第三方能重算这本账。** participant 节点只能看到自己作为 stakeholder
  的合约,不存在全局状态,也没有覆盖其上的公开浏览器或索引服务。传统的替代品
  是审计师出具的核验报告,但它周期性、以文字呈现,而且——最关键的一点——
  资金的所有者本人无法核对。你能读那份报告,却无法在里面找到"自己"。

- **只有平台自己能把账加总。** Canton 是"网络的网络":平台的持仓与用户的头寸
  可能横跨多个 synchronizer 与多个应用,没有任何一个视角能把它们聚合起来。
  这意味着这个数字只能由平台书写——而这恰恰是应当给出用户可验证的承诺、
  而不是要求用户接受一个数字的场景。

- **不存在"截至第 N 个区块"。** 以太坊式的透明度免费继承了一个全网公认的
  时间切点;Canton 的每个 participant 各有自己的有序事件流,"截至何时"必须被
  构造出来、发布出来并钉死——这正是本格式要求快照时间戳与账本高水位的原因
  ([SPEC.md](SPEC.md) §7)。没有它们,快照是不可证伪的:任何不方便的余额都能
  被归因为"时点问题"。

- **这里的赌注是机构级的。** Canton 上是受监管的交易场所、代币化基金与 RWA
  平台,其交易对手方的合规要求是"证据而非保证"——同时又受制于不允许把一切
  公开的保密条款。

- **承诺本来就是 Canton 的原生信任形态。** participant 之间靠周期性交换共享
  合约状态的哈希承诺来发现分歧,而不是把状态本身摊开。发布逐用户的 Merkle
  求和承诺、按需回答"是否被包含"的问题,是同一套模式从"节点对节点"延伸到
  "平台对公众"。这里没有任何一处是逆着网络设计硬接上去的。

## 🔀 为什么不能直接把以太坊的 Proof of Reserves 方案搬过来

因为 Merkle 树只是这个问题里最容易的十分之一,而其余十分之九所依赖的前提,
在 Canton 上一个都不成立。

| 以太坊 PoR 方案默认 | Canton 的现实 | 本方案因此必须 |
|---|---|---|
| **储备是公开的** —— 对已知地址调用 `balanceOf`,区块浏览器与数据看板让任何人免费复核资产侧。 | 托管持仓是 Daml 合约,只对其 stakeholder 可见。既没有可以指向的地址,也没有可供指向的浏览器。 | 把不等式的**两侧**都当作私有数据。资产侧要变成一个公开发布并被承诺的数字,配以自己的核验路径([Milestone 1](#milestone-1--canton-储备核验)),而不是一个指向区块浏览器的链接。 |
| **对储备的控制权可用签名证明** —— 钱包对挑战串签名,地址即身份。 | 持仓是由 party 持有的合约,而不是"某把私钥背后、状态公开可读的余额"。 | 显式核验并披露托管方。树本身从不暗示这一点——见[安全模型](#-安全模型)。 |
| **快照就是一个区块高度** —— "截至区块 N"是权威的,任何人都能据此重算状态。 | 没有全局区块高度;每个 participant 在每条 synchronizer 上各有自己的事件流。 | 把快照时间戳与账本高水位定为规范要求发布的字段,由报告本身把时点钉死。 |
| **余额就是一条账户记录**,从交易所数据库里读出来即可。 | 余额是一个聚合量:活跃持仓合约、在途结算流程中被锁定的额度,在衍生品场所还包括保证金与按标记价格计算的未实现盈亏。 | 把这个推导过程写进规范,而不是留给接入方:负值钳零并作为坏账披露,自营账户剔除**且**披露,标记价格随报告一同公布。 |
| **`uint256` 与整数运算** —— 金额以 wei 计,小数位只是展示问题。 | Daml 的 `Decimal` 是带符号的 `NUMERIC(38,18)`。 | 全链路精确 18 位定点小数、唯一的规范化字符串表示、加法溢出检查——否则两套实现会在最后一位上分歧,所有证明随之失败。 |
| **验证发生在公开合约上**,并且越来越多地交给任何人都能调用的 ZK 验证合约。 | Daml 合约只对其 stakeholder 可见,因此"上链"并不等于"公众可验证"。 | 让验证在用户浏览器里完成。把报告根锚定上链([Milestone 2](#milestone-2--报告根上链锚定))带来的是防篡改历史,而不是公众可验证性;客户端验证始终是信任根。 |

而以太坊生态里现成的那些树,往往正是最不该照抄的对象。以下都不是假想——
每一条都在真实的 PoR 部署中出现过,也都在 [SPEC.md](SPEC.md) 里有对应的
规则堵死:

- **奇数节点复制自身。** 让落单的节点与自己配对求哈希,会把该子树的金额计两遍,
  虚增承诺总额。→ 奇数节点原样**提升**到上一层(§4)。
- **求和不进哈希。** 如果各节点的总额没有被绑进节点哈希,树根可以在"是否包含"
  上诚实、却在"总额"上说谎。→ 每一层都把总额哈希进去,验证时同时比对总额与
  哈希(§4、§5)。
- **会泄露的叶子。** 未加盐的叶子在余额空间很小时可被暴力枚举;跨报告保持不变
  的叶子则让旁观者能长期追踪某个用户。→ `salt = HMAC-SHA256(每次快照的主盐,
  user_id)`,同一用户的叶子哈希在不同快照之间不可关联(§3)。
- **允许负数对冲。** 一个穿仓账户会悄悄抵掉其他用户的余额,平台由此打印出一个
  "偿付充足"的总额。→ 负权益永不进树,钳零后作为坏账披露(§1)。

## 📐 披露 Profile

一个 **profile** = 一条具名的陈述 + 一套叶子结构 + 一张对象权限表。底下的密码学
内核始终不变 —— 这正是它是一份"格式"而不是一个"脚本"的原因。

**所有 profile 共用的部分:** Merkle 求和树及其域分隔哈希、规范化 18 位小数编码、
每次快照的盐派生、包含性证明格式与验证规则、报告信封(格式版本、快照时间、账本
offset、发布方、签名)、锚定链,以及验证端本身。

**逐 profile 变化的部分:** 一片叶子代表什么、树根断言的是哪条陈述、必须公布哪些
聚合量,以及谁有权看到哪一版视图。

| Profile | 被证明的陈述 | 一片叶子是 | 状态 |
|---|---|---|---|
| `solvency.liabilities` | 每一位客户的余额都被承诺,树根总额即负债 | 一位客户的逐资产权益 | **已交付** |
| `solvency.coverage` | 托管持仓 ≥ 负债,逐资产成立 | 一笔托管持仓 | M1 |
| `collateral.repo` | 每一笔未平仓回购都按折扣率足额抵押 | 一条交易腿及其已缴抵押品 | M3 |
| `fund.nav` | 每份额 NAV 由已承诺的持仓按公布标记价格支撑 | 一条持仓明细 / 一位份额持有人 | M3 |
| `settlement.dvp` | 在本时间窗内,没有任何一条腿在对手腿之外单独结清 | 一笔已结算交易 | M3 |
| `eligibility.holder` | 每一位持有人在发行时都满足规则 R | 一位持有人的已核验属性 | M3 |

**披露清单(disclosure manifest)。** 每份报告都携带一份机器可读的清单,逐字段
声明该字段是*已公开*(该对象可见)、*仅承诺*(已被证明但不展示),还是*不披露*。
由于这份清单被绑进已签名并已锚定的报告,机构无法悄悄地比上个季度少披露一些东西
——"少披露"这件事本身就会留在记录里,并以 diff 的形式暴露出来。选择性披露由此
从一个编辑动作变成一个可审计的决定。

**层级结构。** 大机构不是一本账。Merkle 求和树天然可组合:实体层级的树根成为
集团层级树的叶子,于是子公司可以只向自己的监管机构证明自己那棵子树、而不暴露
兄弟实体,同时集团树根依然等于合并总额。

**扩展节点规则。** 有些陈述靠求和不够 —— 集中度限额("任一对手方占比不超过
10%")需要在每个节点上同时携带最大值。这会改变节点哈希,因此它以新的格式版本、
新的域字符串发布,绝不做静默升级(见[版本与兼容性](#-版本与兼容性))。

## ✨ 核心特性

- **Merkle 求和树承诺** —— 每个节点都携带逐资产总额,树根即公开负债数字;漏记
  用户、缩减余额、虚报总额,都会破坏某个用户的证明。
- **用户自助验证** —— 基于 WebCrypto 在浏览器本地完成,数学过程不经过任何
  服务器,无须信任平台。
- **跨实现黄金测试向量** —— Rust 生产端与 TypeScript 验证端断言完全相同的
  字节级向量([SPEC.md](SPEC.md) §6),两套实现不可能悄悄分叉。
- **诚实的边界处理** —— 负权益钳零并作为坏账披露(绝不允许抵消其他用户的
  余额);自营账户剔除并披露;奇数节点提升而非复制。
- **精确算术** —— 全链路 18 位定点小数,与 `NUMERIC(38,18)` 账本无损对应;
  所有加法均做溢出检查。
- **生产环境验证** —— 支撑 [Rocky](https://rocky.exchange)(Canton 原生
  衍生品与现货交易所)的每日偿付报告与公开 Transparency 页面。

## 🖥️ 披露控制台

> **状态:规划中 —— [Milestone 4](#milestone-4--披露控制台)。** 目前参考部署用
> Rust 生产端发布、用 TypeScript 库验证。控制台是让这两件事都能被"不跑脚本的人"
> 使用的那一层。

没人能操作的承诺,算不上透明度基础设施。控制台是同一套格式之上的两个界面。

**发布端 —— 面向披露机构的运营与合规团队**

- 连接 participant 节点、声明 party、选择 profile。无需写代码。
- **披露设计器** —— 逐字段决定哪些公开、哪些仅承诺、哪些不披露,可按对象分别
  设置,并实时预览交易对手方、审计师、监管机构与公众各自将看到的确切内容。
- **发布前 diff** —— 在任何东西发出去之前,先看清相对上一份报告改了什么,新增
  披露**与**新增隐藏都会被单独标出。误披露和"悄悄不再披露"都在这一步被拦住。
- 排程、签名、发布、锚定([Milestone 2](#milestone-2--报告根上链锚定))。

**查看端 —— 面向交易对手方、审计师、监管机构与终端客户**

- **每个数字都带来源标记。** 任何数字都不会在不说明"它是怎么被知道的"的情况下
  显示:*已验证*(在你的浏览器里从承诺重算得出)、*仅声称*(发布方给出的数字,
  未经证明)、*未披露*。让"证明"和"声称"之间的界线无法被忽略,正是这个产品的
  要点。
- **数据流视图** —— 把一个数字背后的 Canton 结构画成图:哪些 party、哪些
  synchronizer、哪些合约类型汇入了每一项小计。这一项正是针对实体层级很深、
  又刚接触 Canton、需要看清数字从哪来的机构。
- **覆盖率视图** —— 逐资产的储备对负债,缺口被标出而不是被抹平。
- **历史视图** —— 锚定链随时间展开;被改写或缺失的报告表现为链条断裂,而不是
  一条脚注。
- **自助核验** —— 把自己的证明文件拖进来,本地离线验证。
- **证据包** —— 导出一份签名归档,审计师多年后仍可用 CLI 离线复核,不依赖发布方
  的基础设施,也不依赖本项目的。

## 🔌 生产端接入

1. **一致性快照** —— 单事务读取;记录账本高水位,把快照钉在事件历史的确定位置。
2. **计算权益** —— 逐用户逐资产;负值钳零并记录坏账;剔除自营账户但披露户数与
   总额。
3. **构建承诺** —— 按稳定用户顺序生成叶子(`leaf_salt` + `leaf_node`),再
   `SumTree::build`。
4. **发布** —— 根哈希、根总额(即负债总额)、标记价格、披露项;向每位用户提供
   其叶子原像与 `tree.prove(i)`。

生产端义务的完整规范见 [SPEC.md](SPEC.md) §7。

## 🔒 安全模型

**验证通过意味着什么:** 你的余额被按向你披露的数值如实承诺;该承诺聚合进公开
树根;树根总额等于全部已承诺叶子之和。

**它本身不证明什么:** 不能证明*每一位*真实用户都在树中(依赖用户抽查——因此
参考部署把验证做成页面上的一次点击),也不能证明资产侧的诚实(托管核验是
[Milestone 1](#milestone-1--canton-储备核验))。频率也有边界:每日快照只承诺
每日状态,不覆盖日内。

发现安全漏洞?请私下报告 —— 见 [SECURITY.md](SECURITY.md)。

### Milestone 0 —— 报告与证明文档

**状态:已完成。** 核心 crate 能对余额做出承诺,却无法"发布":它只返回内存中的
结构,而 SPEC §7 是非规范性的。后续每一个 milestone 都要读写报告文档,所以格式
必须先行。

**已交付**

- `canton-solvency-report` —— 报告信封与证明文档,采用带长度前缀的域分隔摘要
  ([SPEC.md](SPEC.md) §8.2)而非规范化 JSON,因此重新排版文档不会让签名失效。
- **Ed25519 分离签名** —— 对摘要签名,且验证方必须显式传入受信任公钥;文档内

- **报告绑定** —— 每份证明都写明其所属报告的摘要,过期证明无法被拿来对新报告

- **带类型的验证结果** —— 验证方能说清是哪一步没过,包括最关键的那种情况:

### Milestone 1 —— Canton 储备核验

把负债承诺与经核验的托管持仓配对,让报告陈述的是**覆盖率**,而不只是负债。

**交付物**

- `canton-reserve-attest` —— Ledger API 客户端,读取一组声明的托管 party 的
  活跃合约集,并按资产聚合持仓。
- **快照绑定** —— 资产侧读取与负债侧快照钉在*同一个*账本 offset 上,使两侧
  可证明地对应同一时刻,而不是相隔数分钟的两次读取。
- **覆盖率报告格式**(新增 SPEC §11)—— 逐资产的储备、负债与覆盖率,外加托管
  party ID、账本 offset 与标记价格,由平台签名。
- **多资产覆盖率** —— 逐资产分别计算;某一资产的缺口被标红,绝不允许用另一
  资产的盈余来抵平。

**完成标准:** 黄金向量扩展到覆盖率报告,并由两套实现共同断言;在 Canton
localnet 上端到端跑通,从预置的持仓与用户余额产出一份已验证的覆盖率报告;
一条回归测试证明逐资产缺口无法被总量对冲掩盖。

### Milestone 2 —— 报告根上链锚定

让报告历史可发现篡改:平台无法悄悄改写或丢弃某一天的历史报告。

**交付物**

- **Daml 包 `SolvencyReportAnchor`** —— 每份报告一个不可变合约,携带
  `{format_version, report_root, root_sums_hash, snapshot_time,
  ledger_offset, publisher, prev_anchor}`,其 observer 集合可由平台按需
  扩大到审计师、交易对手方或一个公共 observer party。
- **锚定客户端** —— 构建 → 锚定 → 发布,并把锚定合约 ID 写进公开报告。
- **哈希链式历史** —— 每个锚点引用前一个锚点,断链、分叉或被改写的历史报告
  因此是"可被发现"的,而不只是"不太可能发生"。
- **验证端支持** —— 用锚点校验报告,并沿链向前回溯。

**完成标准:** 测试套件证明改写任一历史报告、遗漏某一天或分叉链条都会导致
验证失败;同时明确记录可见性模型及其边界 —— 锚定为能看到该合约的参与方提供
防篡改证据,而不是公众可验证性。

### Milestone 3 —— 选择性披露 Profile

把这套格式从"关于交易所负债的一条陈述",推广成 Canton 上的机构真正需要作出的
那一族陈述。

**交付物**

- **Profile 注册表**(新增 SPEC §14)—— 每个 profile 固定其叶子结构、树根断言的
  陈述、必须公布的聚合量,以及一张默认对象权限表。profile 与核心格式一样,随附
  黄金向量。
- **偿付之外的四个 profile** —— `collateral.repo`、`fund.nav`、
  `settlement.dvp`、`eligibility.holder`,按"真正在往 Canton 上搬的东西"来选:
  回购、代币化基金、DvP 国债结算、许可制发行。
- **披露清单** —— 逐字段的"公开 / 仅承诺 / 不披露"机器可读声明,绑进已签名的
  报告,并可在报告之间做 diff,使"减少披露"这件事本身留在记录里。
- ~~**层级化承诺**~~ —— **已交付**,见 [SPEC.md](SPEC.md) §13。实体树根作为
  集团树的叶子,子公司可只向自己的监管机构证明自己那棵子树而不暴露兄弟实体,
  集团树根仍等于合并总额;客户还能把自己的余额一路验证到集团的合并负债。
  这一项无需破坏线格式:集团树就是一棵叶子为实体的普通 §4 求和树。
- **按对象打包证明** —— 同一份承诺、若干份打包视图,每一份只包含其对象有权看到
  的内容,而且全都归约到同一个树根。

**完成标准:** 每个 profile 都有由两套实现共同断言的黄金向量;一条层级测试证明
在没有兄弟实体数据的情况下,子公司的子树仍能对集团树根验证通过;一条清单 diff
测试能检出被悄悄缩减的披露;并且至少有一个 `solvency.liabilities` 之外的 profile
在 Canton localnet 上端到端跑通。

### Milestone 4 —— 披露控制台

把一份格式变成合规团队能操作、对手方分析师能看懂的东西 —— 这是"一份规范"和
"被采用的基础设施"之间的差别。

**交付物**

- **发布端控制台** —— 节点连接与 party 声明、profile 选择、带分对象实时预览的
  披露设计器、发布前 diff、排程、签名、发布、锚定。
- **查看端控制台** —— 每个数字上的来源标记(已验证 / 仅声称 / 未披露)、每一项
  小计背后由 party、synchronizer 与合约类型构成的数据流图,以及覆盖率视图、
  锚定历史视图和拖入即验的自助核验。
- **验证始终留在客户端** —— 查看端在浏览器里重算证明;服务器只是分发通道,永远
  不是权威。托管实例与可自部署构建同时提供。
- **证据包导出** —— 一份可由 CLI(M5)离线复核的签名归档,不依赖发布方。
- **非技术上手路径** —— 一份从 participant 节点到首份公开报告、全程无需写代码的
  文档化流程,外加一个装有合成回购、基金与结算数据的演示实例。

**完成标准:** 一位既不写 Rust 也不写 TypeScript 的操作者,仅凭控制台就能对
localnet 发布一份符合规范的报告;只要有任何一个渲染出的数字缺少来源标记,构建
即失败;页面加载后屏蔽其源服务器,查看端仍能完成验证;并且该上手流程经过非
Canton 工程师背景的参与者实测验证。

### Milestone 5 —— 独立验证工具包

把发布方彻底移出验证路径。

**已交付部分**

- **`canton-solvency-verify` CLI** —— [`rust/solvency-cli`](rust/solvency-cli)。
  验证单份证明或整目录扫描,打印报告摘要,`--json` 供流水线消费,并把退出码
  `1`(验证未通过)与 `2`(用法或 I/O 错误)区分开,使一个打错的路径永远不会
  被当成资不抵债的证据。必须显式传入受信任公钥 —— 不存在"拿报告自带的公钥
  校验它自己"这种模式。
- **JSON Schema** —— 报告与证明文档的 Schema 置于 [`schemas/`](schemas),
  并在 CI 中对黄金夹具校验。
- **集团相关子命令** —— `verify-group` 校验实体成员资格对集团报告,
  `verify-chain` 把一位客户一路校验到集团合并总额(见 [SPEC.md](SPEC.md) §13)。
  `--group-key` 可单独指定集团发布方公钥,因为集团与其子公司未必用同一把密钥。
- **独立离线验证页** —— [`offline/verifier.html`](offline/verifier.html),
  单个自包含文件,无构建步骤、无网络请求。它内嵌的正是测试套件所覆盖的同一批
  模块,而不是另写一份验证逻辑;页面上每个数字都标注**在本机重算**或
  **发布方声称**,读者一眼就能分清哪些值是这个浏览器证明的、哪些只是发布方
  声称的。可选的集团输入用于校验完整链条(见 [SPEC.md](SPEC.md) §13.4);
  且只要链条未通过,集团相关数字一律标为"发布方声称",不会把未经核验的总额
  伪装成已证明的。一旦仓库内的页面与源码不同步、或引入了外部引用,测试即失败。

**尚未完成**

- 覆盖率报告(M1)、锚定链(M2)与披露清单(M3)对应的 CLI 子命令 —— 在这些
  文档尚未定义之前刻意不提供:一个会静默跳过检查的验证器,比一个干脆不提供该
  检查的验证器更糟。
- 从完整叶子导出重算树根 —— 目前还没有任何组件产出这种导出格式。
- 覆盖率、披露清单与 profile 文档的 Schema。
- crates.io 发布与预编译二进制。
- **生产端参考接入** —— 附样例数据集、有文档的"快照 → 权益 → 树 → 发布"
  路径,与线上的 Rocky 部署互为参照。

**完成标准:** CLI 在公布的时间预算内验证 [SPEC.md](SPEC.md) §6 黄金向量与
一份生产规模的报告(10 万片叶子);仓库内每一份示例文档都在 CI 中通过 schema
校验;上面列出的其余子命令补齐。*离线页面与 schema 校验已完成;10 万片叶子
报告的时间预算尚未实测。*

### Milestone 6 —— 生态标准化

把单一实现变成网络可以依赖的东西。

**交付物**

- **一致性测试套件** —— 一份可执行的测试语料,任何实现都能运行以主张兼容性,
  覆盖线格式、覆盖率报告、锚定、profile 与披露清单。
- **两个独立的 Canton 接入方** —— 至少有一个 Rocky 之外的生产方发布符合规范
  的报告(最好采用另一个 profile),并双向验证互通:对方的报告能被本工具验证,
  本项目的报告也能被对方验证。
- **公开规范 v1.1** —— SPEC.md 增补 §11 覆盖率、§12 锚定与 §14 profile
  (§13 层级化承诺已是规范性内容),并以一致性套件冻结。
- **第三方安全审计** —— 对承诺核心、盐派生与验证端的外部评审,发现的问题与
  修复方案在仓库内公开。
- **CIP 提案** —— 将线格式提交至 Canton Improvement Proposal 流程,以一致性
  套件作为其规范性测试。

**完成标准:** 两套独立实现通过一致性套件;安全审计报告与修复公开;CIP 已提交
并回应完评审意见。*CIP 是否被采纳由 Canton 治理流程决定,不由本项目单方面
决定 —— 交付物是一份已提交并持续维护的提案。*
